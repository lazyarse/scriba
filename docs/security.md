# Security Notes

## Preview Security

Scriba provides several layers of protection for the in-app preview (QWebEngineView).
These are configured in **Preferences → Security → Preview**.

### 1. Strip `<script>` Tags

Removes any `<script>` tags from the rendered markdown HTML before injection.
Scriba's own scripts (highlight.js, Mermaid, KaTeX, ECharts, twemoji) are injected
in the `<head>` of the preview template and are unaffected.

### 2. Block Raw HTML at Parser Level

When enabled, the md4c parser is given the `MD_FLAG_NOHTML` flag
(`MD_FLAG_NOHTMLBLOCKS | MD_FLAG_NOHTMLSPANS`). This tells the parser to
treat any raw HTML in the markdown source as plain text and escape it
(e.g. `<div>` → `&lt;div&gt;`).

This is the strongest protection because it prevents all HTML-based attack
vectors — not just `<script>` tags, but also:
- Inline event handlers (`onclick`, `onerror`, `onload`)
- `<iframe>`, `<object>`, `<embed>` elements
- `javascript:` URLs in links
- Arbitrary `<style>` blocks from user content

Only the structural HTML generated by Scriba's own `MdRenderer` (paragraphs,
headings, tables, lists, etc.) is emitted. User-supplied HTML is always escaped.

### 3. Content Security Policy (CSP)

A `<meta http-equiv="Content-Security-Policy">` tag is injected into the
preview HTML `<head>` when enabled (default: on).

The policy used is:

```http
default-src 'self' qrc:;
script-src 'self' qrc: 'unsafe-inline' 'unsafe-eval';
style-src 'self' qrc: 'unsafe-inline';
img-src 'self' qrc: data: file:;
font-src 'self' qrc: data:;
connect-src 'self' qrc: data: blob:;
```

#### Why `'unsafe-inline'` and `'unsafe-eval'` are required

Both `script-src` and `style-src` include `'unsafe-inline'` because Scriba's
bundled JavaScript libraries and the application's own initialisation code
use inline scripts and styles:

| Component | Why inline is needed |
|---|---|
| **App initialisation** | The `scribaUpdate()` function, click handler, and `DOMContentLoaded` bootstrap are inline `<script>` blocks injected by the C++ backend |
| **KaTeX** | Renders LaTeX into DOM elements with inline `style` attributes for precise math spacing |
| **Mermaid** | Uses inline `<style>` in SVG output; initialization is done via inline `mermaid.initialize()` call |
| **highlight.js** | `hljs.highlightAll()` is called from an inline script after DOM population |
| **ECharts** | Charts are embedded via inline `<script>` with JSON option specs |

The `script-src` retains `'unsafe-eval'` for compatibility: ECharts compiles
optional geo-JSON map data via `new Function()` at runtime, and it is kept in
place rather than risk breaking chart rendering on future library updates.

A strict CSP (without `'unsafe-inline'` and `'unsafe-eval'`) would break all
rendering. There is no way to use nonces or hashes here because the HTML is
dynamically generated by the C++ application at runtime, and the inline scripts
are constructed via string concatenation in `MainWindow::updatePreview()`.

#### What the CSP blocks

Despite the `'unsafe-inline'` allowances, this CSP still blocks:

- **Inline event handlers** — `<img src=x onerror="alert(1)">` will not fire
  because `onerror` is an inline event handler, not a `<script>` block. CSP
  blocks all `on*` event attributes regardless of `'unsafe-inline'`.
- **`javascript:` URLs** — `<a href="javascript:alert(1)">` is blocked.
- **External network requests** — `fetch()`, `XMLHttpRequest`, WebSocket to
  origins other than `self`, `qrc:`, `data:`, or `blob:` are blocked.
- **External script loads** — `<script src="https://evil.com/x.js">` is blocked.
- **`<base>` URI redirection** — the `default-src` limits script/style sources.

#### CSP export

The same CSP is also applied to exported HTML files (PDF, DOCX, HTML) when
the export CSP setting is enabled. This means exported files retain the same
security properties as the preview.

## Export Security

Configured in **Preferences → Security → Export (PDF, DOCX, HTML)**.
These settings mirror the preview protections but apply during file export.

### Script Handling

During HTML export, the **Export HTML** dialog additionally offers a per-export
choice between stripping scripts and embedding external ones. The global
"Strip `<script>` tags" preference sets the default.

### Raw HTML Blocking

When enabled, `MD_FLAG_NOHTML` is passed to the parser during export, the same
as for preview. Exported HTML will contain escaped HTML entities instead of
raw user-supplied markup.

### CSP in Exports

When enabled, the same CSP meta tag is injected into:
- **PDF export** — the intermediate HTML that is converted to PDF via
  QWebEnginePage's `printToPdf()` includes the CSP meta tag.
- **DOCX export** — the rendered HTML passed to the DOCX converter includes
  the CSP meta tag.
- **HTML export** — the final `.html` file includes the CSP meta tag in its
  `<head>`.

## HTML Export — Image Handling

When exporting a Markdown document as HTML, Scriba embeds all images inline as
`data:` URIs. This applies to both local images (resolved relative to the
source `.md` file) and external images (fetched over HTTPS at export time).

### Why fetch external images?

Leaving external URLs in the exported HTML would cause the viewer's browser to
contact third-party servers on every open — enabling tracking, fingerprinting,
and the potential serving of different (possibly malicious) content on
subsequent requests.

By fetching and embedding at export time:

- No runtime network requests remain in the exported file.
- The exported HTML is fully self-contained and works offline.
- The image content is static and immutable once embedded.

### Validation

Downloaded images are validated before embedding:

- The MIME type is checked via `QMimeDatabase` — only recognised image types
  (`image/*`) are embedded.
- If the fetch fails (network error, non-image response, timeout), the original
  URL is preserved as a graceful fallback.

### Limitations

- Large images significantly increase file size.
- Export requires network access when external images are present in the
  document.
- Embedded images are frozen at export time — updates to the source image are
  not reflected in previously exported files.

## HTML Export — Script Handling

Raw HTML in markdown can include `<script>` tags that reference external
JavaScript files. During export, the user can choose how these are handled:

### Strip (default)

All `<script>` tags — both inline and external — are removed from the exported
HTML. This is the safest option: no JavaScript runs in the exported file, and
there are zero external network requests.

### Embed external

External `<script src="URL">` tags are fetched at export time, and the JS
content is inlined into the `<body>` of the exported HTML. The `src` attribute
is removed. Inline `<script>` blocks (without a `src` attribute) are left
unchanged.

**Security note:** Inline scripts may still contain code that makes network
requests at view time (e.g. `fetch()`, `XMLHttpRequest`, dynamic `<script>`
injection). Choosing "Embed external" does not eliminate this risk — it only
prevents the external-script-to-inline conversion vector. If you require zero
network requests at view time, use "Strip".

### Export-time Only

Note that the export dialog script handling is separate from the global "Strip
scripts" preference. The dialog lets you choose per-export; the global
preference sets the initial state.

## HTML Export — External CSS (`<link>`)

External stylesheets referenced via `<link rel="stylesheet" href="URL">` are
**always** fetched and inlined as `<style>` blocks during export. This applies
to both HTML and DOCX export and is not affected by the script-handling option.
CSS is declarative and cannot execute code, so embedding it carries no
execution risk.

## Defense in Depth

Scriba uses a layered approach to security — no single measure is relied upon:

1. **Parser-level escaping** (`MD_FLAG_NOHTML`) — prevents raw HTML from
   entering the output at all. This is the strongest, earliest layer.
2. **Script tag stripping** — catches `<script>` elements that might slip
   through or be intentionally embedded.
3. **Content Security Policy** — a browser-enforced safety net that blocks
   inline event handlers, `javascript:` URLs, and external resources even if
   HTML does reach the DOM.
4. **Navigation controls** — link clicks in the preview are intercepted and
   validated; only `file://` URLs with `.md` extension are opened internally;
   all other URLs open in the system browser.
5. **No WebChannel bridge** — there is no bidirectional JS→C++ communication
   channel that could be exploited. All communication is one-way: C++ calls
   `runJavaScript()` with escaped arguments.
